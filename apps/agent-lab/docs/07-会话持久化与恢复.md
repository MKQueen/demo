# 第 7 章：会话持久化与恢复

> **本章目标**：搞清楚 Agent 为什么必须"记账"、为什么账本用 JSONL 而不是一个大 JSON，
> 以及 `create` / `load` / `list` 背后的取舍。重点是一个真实踩过的坑：
> 主循环和持久化层都往历史里 push，结果消息重复、mock 剧本跳幕。
>
> 预计：30 分钟。对应代码：`src/session.ts`、`src/agent/loop.ts`（`SessionSink`）、`src/main.ts`（`--session` / `/sessions` / `/new`）。

## 7.1 先建立直觉：Agent 需要一本"账本"，不是一张"存档卡"

第 0 章说过：模型没有记忆，所谓多轮对话，是你每次把全部历史重新发过去。这段历史就躺在进程内存的 `ChatMessage[]` 数组里。于是：关终端 → 没了；程序崩 → 几十轮白跑；想复盘它读了什么、跑了什么 → 毫无痕迹。

内存里的 `history` 是**黑板**，写着当前这一局；磁盘上的会话文件是**账本**，每发生一件事就登记一行。黑板擦了没关系，账本还在，照账本把黑板重写出来就行。

所以"恢复会话"的本质不是读存档，而是**重放（replay）**：

```
磁盘账本 ──逐行读──▶ message 行逐条追加 / snapshot 行覆盖 ──▶ 拼回 history 数组 ──▶ 继续跑
```

账本里还有工具执行、压缩等行，它们是**审计日志**，重放时不用（`snapshot` 例外，它就是为了重放而生的）。这个区分是本章的关键。

## 7.2 核心概念逐条拆

### 概念 1：Session 与会话 id

一次"从启动到退出"的对话是一个会话（session）。两个决策：**会话落在项目里**（`<项目>/.mini-opencode/sessions/<id>.jsonl`，`sessionsDir`），复制项目就能看到历史，代价是要记得排除出 git；**id = 时间戳 + 随机串**（`src/util.ts` 的 `shortId()` 生成 `20261102-104335-msnk`），按时间天然排序、肉眼可读，但不是 UUID。

元信息 `SessionMeta` 记录 `id`、`createdAt`、`cwd`、`model`。记下 `cwd` 很有用——它告诉你会话在哪个目录开的。

### 概念 2：JSONL（JSON Lines）

规则只有一条：**每行一个完整 JSON 对象**。为什么不是一个大的 JSON 数组？因为大 JSON 每次追加都要重写整个文件，中途崩溃整个文件报废，读取还得全量进内存；JSONL 追加一行就行，最多坏最后一行，可以逐行流式读。

Agent 会话可能几十 MB（工具输出极长），每次追加都重写文件不可接受。JSONL 还天然是**事件日志（event log）**：只在尾部追加、不破坏旧内容。据第 0 章对照表，真实 opencode 用 SQLite 存会话、支持事件溯源（event sourcing）；我们选 JSONL 是因为它零依赖、能 `cat`、能 `tail -f`，是"事件日志"最直观的形态。

### 概念 3：六种事件行

会话文件头部注释（`src/session.ts`）写明了前五种：

```ts
//   {"type":"meta","meta":{...}}        ← 第一行：会话元信息
//   {"type":"message","message":{...}}  ← 一条对话消息（user/assistant/tool）
//   {"type":"tool","name":"bash",...}   ← 工具执行事件（只用于审计，重建历史不靠它）
//   {"type":"compaction",...}           ← 上下文压缩事件
//   {"type":"snapshot","messages":[...]} ← 历史快照（压缩后用一条新快照“逻辑覆盖”旧消息）
```

实际还有第六种 `turn_end`（每回合由 `src/main.ts` 写，记录步数、usage、是否中断/被权限拒绝）。一张表说清：

| 行类型 | 谁写的 | 内容 | 重放吗 |
| --- | --- | --- | --- |
| `meta` | `Session.create` | id、时间、cwd、model | 读来校验 |
| `message` | `persistMessage` / `appendMessage` | 完整 `ChatMessage` | **是**，逐条追加 |
| `tool` | `appendEvent`（`loop.ts`） | 工具名、参数、isError、耗时 | 否，审计 |
| `compaction` | `appendEvent`（`loop.ts`/`main.ts`） | 压缩前后 token、摘要 | 否，审计 |
| `snapshot` | `appendSnapshot`（`main.ts`/`loop.ts`） | 压缩后的完整历史数组 | **是**，清空旧消息后以它为准 |
| `turn_end` | `appendEvent`（`main.ts`） | 步数、usage、是否中断、toolDenials | 否，统计 |

**为什么 `tool` 行不能当消息喂模型？** 协议要求 `tool` 消息必须紧跟带 `tool_calls` 的 `assistant` 消息，审计行没有 `tool_call_id` 的对应关系；而且完整工具输出已经作为 `message` 存过一份，再喂一次就是重复。账本不等于账。

### 概念 4：恢复 = 重放 message 行，snapshot 一票否决

`Session.load` 做的事很"笨"，也正因为笨而可靠：逐行 `JSON.parse`；遇到 `message` 行就追加；遇到 `snapshot` 行就把已经收集的 `messages` **清空并替换**成快照里的数组；坏行 `continue`；没有 `meta` 行就报错。

快照是"追加写日志"实现"逻辑覆盖"的关键：JSONL 不能删旧行，压缩后旧消息还躺在文件里，如果恢复时照单全收，压缩就白做了。`snapshot` 行相当于在账本里写一笔"从这个时点起，历史以这份为准"：审计时旧行还在，恢复时以最新快照为起点。

坏行跳过值得单独说：进程被 kill 时文件尾部可能只写了半行，但**之前**的对话是完好的。一行坏掉不影响前面几十行——这就是 JSONL 的容错收益。

### 概念 5：三个 API，以及一个"有损"的真相

`Session.create({ cwd, model })` 建目录、生成 meta、**立刻写第一行 meta**——哪怕第一轮就崩，磁盘上也有带 meta 的空会话，`load` 不会误判为损坏。`Session.load(cwd, id)` 先校验 id 只含安全字符（防 `--session ../../x` 读到目录外），找不到文件、没有 meta 行都抛中文错误。`Session.list(cwd)` 扫目录，遇到 snapshot 就以快照为基准重新统计（压缩前的旧 message 不再计入），标题优先从快照里找第一条 user 消息，按文件 mtime 倒序；标题不单独存字段，省了索引维护。

但注意：压缩后的历史能恢复（靠 snapshot），可下面这些**内存态**恢复后仍然会丢：

| 状态 | 存哪 | 恢复后 |
| --- | --- | --- |
| `messages` | 磁盘 message / snapshot 行 | ✅ 重放回来 |
| `toolState`（todo） | 磁盘 `todos` 行 → `Session.toolState` | ✅ 重放回来（7.3.8 讲为什么） |
| 权限"本会话始终允许" | `Permissions.sessionAllowed` | ❌ 新实例，重新问 |
| 模式（build/plan）、yolo | `App` 运行态 | ❌ 回默认值 |
| 模型 | `SessionMeta.model` 只是记录 | ⚠️ 不自动切换，用 `--model` 指定 |

会话文件是**对话日志**，不是**进程快照**——两个不同的东西。

### 概念 6：历史数组的所有权（ownership）——本章最值钱的经验

最早的主循环里，每条消息先 `history.push(message)`，又调用 `session.appendMessage(message)`；而 `appendMessage` 内部又 push 一次。偏偏 `session.messages` 就是主循环用的那个 `history` 数组（`main.ts` 把 `this.session.messages` 传给了 `runAgent`）。结果**每条消息都进两次**。

症状很怪：模型看到两份相同对话，token 翻倍、开始重复回答；mock 更明显——它靠"最后一条 user 消息之后有几条 tool 消息"决定演到第几幕（`src/llm/mock.ts` 的 `toolResultsSinceLastUser`），重复计数让步数翻倍，剧本一步跳两幕，中间的工具调用凭空消失。

修复就是拆成两个方法：`persistMessage`（**只落盘**，主循环用）和 `appendMessage`（**内存+落盘**，`main.ts` 这种主循环外场景用）。原则：**一个数组只能有一个人负责写内存**，持久化层是记录员，不是第二个作者。

## 7.3 代码导览

### 7.3.1 数据结构：没有数据库层

`Session` 类只有四个字段：`meta`（元信息）、`messages`（历史）、`toolState`（内存状态）、`file`（磁盘路径）。`sessionsDir(cwd)` 只是 `path.join(cwd, ".mini-opencode", "sessions")`。没有 Repository、没有 ORM：`messages` 是普通数组，`file` 是普通路径，教学项目的取舍是让你直接看见数据的形状。

### 7.3.2 create：先写 meta，再做别的

`create` 做的事是"建目录 → 生成 meta → 拼文件路径 → `writeLine({ type: "meta", meta })` → 返回对象"。`recursive: true` 保证目录不存在也能跑；文件名直接用 id，不按日期分目录——真实项目会话上百万时才需要。

### 7.3.3 load：只认 message 与 snapshot，坏行放过

```ts
  /** 从磁盘恢复会话。 */
  static load(cwd: string, id: string): Session {
    // …（省略：assertSafeSessionId(id)、拼 file 路径、文件存在性检查）
    const lines = fs.readFileSync(file, "utf8").split("\n").filter(Boolean);
    let meta: SessionMeta | null = null;
    const messages: ChatMessage[] = [];

    for (const line of lines) {
      let parsed: { type?: string; meta?: SessionMeta;
        message?: ChatMessage; messages?: ChatMessage[] };
      try {
        parsed = JSON.parse(line);
      } catch {
        continue; // 坏行跳过，不影响其他内容
      }
      if (parsed.type === "meta" && parsed.meta) {
        meta = parsed.meta;
      } else if (parsed.type === "snapshot" && Array.isArray(parsed.messages)) {
        // 快照 = “从这里开始，历史以我为准”。压缩后恢复靠它。
        messages.length = 0;
        messages.push(...parsed.messages);
      } else if (parsed.type === "message" && parsed.message) {
        messages.push(parsed.message);
      }
    }

    if (!meta) throw new Error(`会话文件损坏（没有 meta 行）：${file}`);
    const session = new Session(meta, file);
    // …（省略：session.messages.push(...messages); return session;）
  }
```

逐段看：`filter(Boolean)` 清掉末尾空行；`try/catch` 里 `continue` 而不是 `throw`；`snapshot` 分支先 `messages.length = 0` 再填快照，这就是"逻辑覆盖"的全部实现；没有 meta 说明文件不是本程序产生的（或被人改坏），拒绝比"猜"安全；恢复时直接 `push(...)`，**不调用 `appendMessage`**——否则旧消息会被重新写一遍回磁盘。

### 7.3.4 三个写方法：appendMessage / persistMessage / appendSnapshot

```ts
  /** 追加一条消息（更新内存 + 落盘）。给 main 这种“不经过 loop”的场景用。 */
  appendMessage(message: ChatMessage): void {
    this.messages.push(message);
    this.persistMessage(message);
  }

  // 只落盘、不改内存。……历史数组的所有权归主循环，Session 只是“记录员”。
  persistMessage(message: ChatMessage): void {
    this.writeLine({ type: "message", message, at: nowIso() });
  }

  // 写一条历史快照。JSONL 不能删旧行，快照表达“从这里开始，历史以这份为准”。
  appendSnapshot(messages: ChatMessage[]): void {
    this.writeLine({ type: "snapshot", messages, at: nowIso() });
  }
```

（`persistMessage` / `appendSnapshot` 的注释有删减，原文完整解释了踩坑过程，值得去源码里读一遍。）反面示例：主循环里 `history.push` 之后千万别再调 `appendMessage`——它内部会再 push 一次，历史里就有两份了。

`appendSnapshot` 是唯一会写 `snapshot` 行的地方，参数是**完整历史数组**。谁调用它？手动 `/compact`（`main.ts` 的 `handleCompact`）和主循环自动压缩（`loop.ts`）在改完 `history` 之后都会调一次。注意文件不会因此变小（旧 message 行还在），但从这一刻起恢复以快照为准。

### 7.3.5 SessionSink：主循环只认接口

主循环不知道 `Session` 类存在，只认最小接口（`src/agent/loop.ts`）：

```ts
export interface SessionSink {
  persistMessage(message: ChatMessage): void;
  appendEvent(event: Record<string, unknown>): void;
  appendSnapshot?(messages: ChatMessage[]): void; // 压缩后重写历史
}
```

调用点成对出现：先 push 内存，再落盘。

```ts
    history.push(assistantMessage);
    options.session?.persistMessage(assistantMessage);
    // …（工具消息同理：deps.history.push(toolMessage); deps.session?.persistMessage(toolMessage)）
```

接口**故意没有 appendMessage**，从设计上堵死"主循环顺手更新内存"；`appendSnapshot` 是可选方法，自动压缩那一段会调 `options.session?.appendSnapshot?.(history)`。测试里干脆传 `undefined`（`session?: SessionSink`），循环照样跑——持久化是可选增强，不是核心依赖。

### 7.3.6 list 的取舍

`list` 的骨架是 `readdirSync` 过滤 `.jsonl` → 逐个 `statSync` 拿 mtime → 逐行统计：普通 `message` 行累加，遇到 `snapshot` 就把计数重置为快照长度、并从快照里重新找标题 → 按 `updatedAt` 倒序。两个细节：坏文件/坏行都不会中断列表；`updatedAt` 用文件修改时间而不是消息里的 `at`（够用，但手动改时间戳会乱）。`/sessions` 与 `node src/main.ts sessions` 共用它，只是渲染不同。

### 7.3.7 归档与删除：为什么归档也写成事件

会话越攒越多时，光靠“导出”解决不了列表噪音。我们加了两种清理方式：

- **归档（archive）**：往 JSONL 追加一行 `{"type":"archive"}`（取消归档追加 `unarchive`）。`Session.list` 逐行扫描时记录“最后一条状态事件”，默认只返回未归档会话；`includeArchived: true` 时连归档项一起返回。**文件不动**，`load` / 导出 / 恢复都不受影响，所以随时能恢复。
- **删除（remove）**：直接 `unlink` 掉 `<id>.jsonl`，不可撤销，网页端会二次确认。

为什么归档不把文件挪到 `sessions/archive/`？因为挪文件会让“当前会话”的文件路径失效，还要额外维护恢复入口；而 JSONL 本来就是 append-only 的事件流，追加一行状态事件最贴合它的模型，也保留审计痕迹（能看到什么时候归档的）。代价是文件不会被物理清理——这是有意的取舍：**归档管的是“看什么”，不是“占多少磁盘”**。

服务端对应三个接口：`POST /api/session/<id>/archive`、`POST /api/session/<id>/unarchive`、`DELETE /api/session/<id>`；删除当前会话会返回 409，因为内存里的 `Session` 还指着那个文件，删了之后下一次写消息会重建出没有 meta 的坏文件。

### 7.3.8 todo 清单：状态该属于谁

`toolState` 最早只是一个内存对象（`Session.toolState`），todo 写进去就完事。
它带来两个方向相反的毛病，而且**修其中一个就会踩到另一个**：

| 做法 | 症状 |
| --- | --- |
| 状态挂在会话对象上（不落盘） | 切走再切回来，清单空了；服务重启，进度全丢 → Agent "忘了自己做到第几步" |
| 状态挂成全局（进程级单例） | 新建会话还显示上一个任务的待办 → 用户以为删不掉 |

所以问题不是"存不存"，而是**归属**：todo 是"这个会话做到哪一步了"，
它必须**属于会话、跟着会话的 JSONL 走**。

实现只有三小步（都在 30 行以内）：

1. **落盘**：`Session.persistTodos(todos)` 追加一行 `{"type":"todos","todos":[...]}`。
   写整份清单而不是增量——`todowrite` 的语义本来就是"整表替换"，
   读的时候"最后一条生效"即可，不需要重放 diff（和 `archive` 事件同一个思路）。
2. **恢复**：`Session.load` 扫到 `type === "todos"` 就记下来，最后塞回 `toolState.todos`。
   于是 `/todos`、侧栏待办面板、和下一回合的模型上下文都是对的。
3. **接线**：工具不该知道会话文件长什么样，所以 `ToolContext` 只加一个回调
   `onStateChange?: (state) => void`；`todowrite` 改完 `ctx.state.todos` 调一下，
   web / CLI 各自把它接到 `session.persistTodos` 上。**工具负责改，宿主负责存。**

还要处理一个边界：**上一件事已经全部完成的旧清单不该继续挂着**。
网页端在 `startRun` 里判断"清单非空且全部 completed"就清空——
而且清空也要落盘，否则切回来那份"已完成"的清单会从 JSONL 里复活。

这条经验可以推广到所有"Agent 工作记忆"：权限的"本会话始终允许"、
模式、当前计划……凡是影响**行为**的状态，都要问一句
**它的生命周期是多长**（一次工具调用？一个会话？整个进程？），
生命周期决定它该存在哪，而不是"先放内存，出问题再说"。

### 实验 4：`/compact` 之后，快照让恢复回到"压缩后"

```bash
cd /tmp && rm -rf mo-snap && mkdir mo-snap && cd mo-snap
printf '你好\n用 todo 拆解一下这个任务\n你好\n/compact\n/exit\n' | node /Users/one/Web/LearningDemo/mini-opencode/src/main.ts chat --mock --yolo
node /Users/one/Web/LearningDemo/mini-opencode/src/main.ts sessions
grep -c '"type":"snapshot"' .mini-opencode/sessions/*.jsonl
```

预期：`/sessions` 显示 **9 条**（压缩前是 10 条）；`grep -c` 输出 `1`。此时旧 message 行仍在文件里（审计可查），但恢复时遇到 snapshot 会先清空再以快照为准，所以 `--session` 恢复出来是 9 条，而不是压缩前的 10 条。想自己验证：用 `Session.load` 读一下，`messages.length` 就是 9。

## 7.5 常见坑

| 坑 | 症状 | 原因 | 怎么避免 |
| --- | --- | --- | --- |
| 主循环两边都 push | 重复回答、token 翻倍、mock 剧本跳幕 | `history.push` 与 `appendMessage` 内部 push 叠加 | 主循环只用 `persistMessage` |
| 把 tool/compaction 行当消息重放 | API 400 或历史错乱 | `tool` 消息必须对应前面的 `tool_calls` | message 行收集、snapshot 覆盖、其余行跳过 |
| 以为恢复等于恢复现场 | 权限重新问、模式回 build | 会话文件只存对话与状态事件 | 跨进程状态显式落盘或用参数指定 |
| 把 todo 当全局状态 | 新建会话还显示上一个任务的清单 | `toolState` 挂在进程而不是会话上 | 状态归属会话，随 JSONL 走（7.3.8） |
| 以为追加写日志"删不掉旧消息" | 压缩后恢复又读到压缩前的历史 | JSONL 不能删行，只能追加 | 用 snapshot 做逻辑覆盖：恢复时清空旧消息，审计仍保留旧行 |
| 手改会话文件或提交 `.mini-opencode/` | 坏行被静默跳过；代码片段和对话进 git | JSONL 对单行损坏静默容错；`.gitignore` 可被 `-f` 绕过 | 只读分析别手改，别 `git add -f` |

## 7.6 本章小结

- Agent 必须持久化：模型无记忆、进程会死、用户要明天继续、审计要证据。
- 选 JSONL 而非大 JSON：追加写、抗单行损坏、可流式读；真实 opencode 用 SQLite + 事件溯源，是更强的同类方案。
- 会话文件是事件日志：`meta` / `message` / `tool` / `compaction` / `snapshot` / `turn_end`，恢复时 message 行逐条追加，snapshot 行清空后覆盖。
- `create` 立刻写 meta；`load` 逐行解析、坏行跳过、snapshot 重置历史、无 meta 报错；`list` 以快照为基准统计，按 mtime 倒序。
- 核心架构约定：**历史数组所有权归主循环**，`SessionSink` 只暴露 `persistMessage`（落盘）、`appendEvent`（审计）和可选的 `appendSnapshot`（压缩后逻辑覆盖）。
- 这个约定来自真实事故：两边都 push → 消息重复 → token 翻倍、mock 跳幕。
- 追加写日志没法删旧行，`snapshot` 用"逻辑覆盖"解决了压缩后的恢复问题（旧行留作审计）。
- 归档同样用"追加事件"实现：`archive` / `unarchive` 只影响列表是否显示，文件始终保留；真正释放磁盘要用删除。
- 恢复仍有损：`toolState`、权限记忆、模式、yolo、模型都不会从会话文件恢复。
- 隐私：会话文件包含代码片段和对话，`.mini-opencode/` 绝不进 git。
