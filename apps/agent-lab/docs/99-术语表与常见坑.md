## 99.2 20 个常见坑

> 每条都来自这个项目的真实代码路径。先看症状，能对上再读原因和解决。

### 坑 1：模型不调工具，只会聊天

- **症状**：明明注册了工具，模型却只回文字，不请求 `read`/`bash`；或者 mock 下只演默认剧本。
- **原因**：请求里没带 `tools`（`hasTools` 为 false 时工具调用被忽略）；提示词里没说明"何时该用哪个工具"；任务本身不需要工具；mock 只认关键词剧本。
- **解决**：检查 `registry.toDefinitions()` 是否传进 `provider.stream` 的 `options.tools`；在工具 `description` 里写清适用场景；换真模型时把任务说得更具体（"先 read 这个文件"）。

### 坑 2：工具参数 JSON 坏了，程序直接崩

- **症状**：模型返回 `arguments` 少引号、多逗号，`JSON.parse` 抛异常。
- **原因**：模型是逐 token 生成文本，长参数容易手滑；流式分片拼接也可能拼坏。
- **解决**：**绝不**让解析异常冒到主流程。`src/agent/loop.ts:460-474` 捕获后把错误原文和"请重新生成合法 JSON"作为 tool 结果喂回模型，模型下一轮会自己改。验证测试见 `test/loop.test.ts`。

### 坑 3：参数名/类型不对（`file_path` vs `path`）

- **症状**：工具收不到参数，或报"未知参数"。
- **原因**：模型按训练习惯写 `file_path`，而 `read` 工具定义的是 `path`；或把 `limit: 10` 写成 `"10"`。
- **解决**：`additionalProperties: false` + 手写校验器（`src/tools/registry.ts`）会明确告诉模型"出现未知参数 file_path（只接受 path）"；报错信息本身就是纠错提示，不要吞掉。

### 坑 4：`tool_call_id` 对不上，接口报错

- **症状**：第二轮请求直接 400，提示 tool 消息没有对应调用。
- **原因**：`assistant` 消息里的 `tool_calls[].id` 与 `tool` 消息的 `tool_call_id` 不一致；或漏了某条工具结果。
- **解决**：`src/agent/loop.ts:412-421` 用同一个 `call.id` 生成每条 tool 消息；**每个** `tool_call` 都必须有回应，包括失败和未知工具。不要手改 id。

### 坑 5：历史里出现重复消息，模型"失忆"

- **症状**：模型收到两份相同的用户问题，token 翻倍，行为错乱。
- **原因**：`Session.appendMessage` 既 push 内存又落盘，而主循环也 push 了 history；两边各加一次。
- **解决**：约定"历史数组的所有权归主循环"，`Session` 只做记录员——所以有 `persistMessage`（只落盘）和 `appendMessage`（两者都做）两个方法，`loop.ts` 只用前者（`src/session.ts:203-213` 注释里写了"这个问题我们真的踩过"）。

### 坑 6：上下文爆了（400/413 或直接截断）

- **症状**：跑十几步后 API 报 `context length exceeded`；或模型开始"忘记"前面的事。
- **原因**：`read`/`bash` 的单条输出可能几万 token，历史指数膨胀。
- **解决**：三层防御在 `src/agent/context.ts`：先截断单条工具输出（`MAX_TOOL_OUTPUT_CHARS = 2000`），再按整轮删旧消息（`fitContext`），最后 LLM 摘要（`compactHistory`）。调大 `--budget` 只能续命，不能根治。

### 坑 7：压缩后目标丢了 / 压缩本身失败

- **症状**：摘要生成后模型不记得原来的任务；或压缩请求返回空、抛"历史太短"。
- **原因**：摘要提示词没要求保留"用户目标、已完成动作、当前状态"；压缩切点必须落在"轮边界"上，找不到可压缩的历史（只剩一轮）时会抛"历史太短"。
- **解决**：`compactHistory` 的摘要 system 里已经写死这些要求；压缩成功后 `loop.ts` / `/compact` 都会写一条 `snapshot` 行持久化（恢复时以快照为准）；压缩失败时 `loop.ts` 会退回裁剪继续（压缩不是致命错误）。太短的历史不要压，直接裁剪即可。

### 坑 8：`edit` 匹配不到 `oldString`

- **症状**：模型说"已修改"，实际报"在 xx 里找不到要替换的原文"。
- **原因**：缩进/空格/换行不一致；文件在模型读取后又被改过；模型凭记忆编了原文。
- **解决**：工具会返回三类常见原因并提示"先 read 重新确认"。给模型的规则也要写死："修改前必须 read"。测试里可以故意给错 oldString 验证错误信息。

### 坑 9：`edit` 匹配到多处，不确定性爆炸

- **症状**：报 `匹配到 N 处，不唯一`，或替换到了不该改的位置。
- **原因**：`oldString` 太短（比如只有 `return`），文件里到处都是。
- **解决**：提供更长的上下文让匹配唯一，或显式 `replaceAll: true`。这个约束在工具描述里，模型看得到。

### 坑 10：`write` 覆盖了没读过的内容

- **症状**：模型新建文件时把已有文件整个覆盖，丢了代码。
- **原因**：模型没先 `read`，直接 `write`；工具层只负责写，不知道"是否读过"。
- **解决**：提示词强制"改已有文件优先 `edit`，新建才 `write`"；权限层对 `write` 默认 `ask`，人能拦一道；更进一步可以在会话状态里记录"已读文件"，`write` 时校验（练习方向）。

### 坑 11：危险命令没拦住

- **症状**：模型执行了 `rm -rf ~/xxx`、`sudo ...`，权限层没弹窗。
- **原因**：`looksDangerous` 只是正则粗筛（`src/tools/bash.ts:52-67`），变形命令、脚本文件、`eval` 都能绕过；权限层也不是沙箱。
- **解决**：危险命中时**至少**转 `ask`（`src/permission.ts:110-123`）；即使之前在本工具上选过 `always`，危险命令也不会被放行（danger 检查在 always 判断之前）；`bash` 默认 `ask`；真隔离要靠容器/受限用户/网络隔离。把"正则拦截"当提示层，别当安全边界。

### 坑 12：非交互终端下所有 ask 都变成拒绝

- **症状**：管道/CI 里跑 `node src/main.ts run ...`，`write`/`bash` 全部失败，提示"需要确认但当前不是交互式终端"。
- **原因**：`interactive = process.stdin.isTTY === true`；没有 TTY 就没法弹窗，`Permissions.check` 对 `ask` 直接返回拒绝。
- **解决**：交互式终端里跑；或在受控学习环境加 `--yolo`；生产 CI 应该显式配置允许的工具/命令白名单，而不是无脑 yolo。

### 坑 13：macOS 上符号链接路径导致 glob 匹配不上

- **症状**：`glob` 返回空，或 `read` 说路径越界；明明文件存在。
- **原因**：macOS 的 `/var` 实际指向 `/private/var`。一边用 `realpath`、一边用原始路径，`path.relative` 会算出 `../../..`。
- **解决**：`src/tools/files.ts` 的 `toRel` 和 `resolveInside` 都对 cwd/路径做 `realpathSync` 后再比较；`resolveInside` 还会从目标向上找第一个已存在的祖先再校验，防符号链接逃逸。

### 坑 14：路径越界 / 符号链接逃逸

- **症状**：模型读到了工作目录外的 `/etc/passwd`，或通过项目里的 `link -> /etc` 绕出去。
- **原因**：只做了 `path.resolve` 字符串判断，没处理符号链接；或先判断后 realpath。
- **解决**：`resolveInside` 会从目标路径向上找**第一个已存在的祖先**做 realpath 检查，所以 `link/new.txt`（目标文件还不存在）也会被拦下；任何越界都返回错误原文，让模型知道被拒绝。这个漏洞是写文档的同事实测发现的，后来补了两条回归测试（`resolveInside: 拒绝通过符号链接目录逃逸…`、`write: 不会通过符号链接把文件写到工作目录外`）——说明**文档审阅和测试都能发现安全 bug**。

### 坑 15：重定向日志里全是 ANSI 转义符

- **症状**：`node src/main.ts run ... > out.log` 后，日志里出现 `[36m`、`[0m` 之类乱码。
- **原因**：`Renderer` 的输出如果不是走 `ansi.ts`（比如你在工具或日志里自己拼了带色字符串），就不会受 TTY 门控；`NO_COLOR` 也只在走统一函数时才生效。
- **解决**：所有输出走 `src/ui/ansi.ts`；它用 `process.stdout.isTTY === true && !process.env.NO_COLOR` 统一控制，`clearLine()` 在非 TTY 时退化为换行。新增输出也必须走这些函数，不要手写 `\x1b[...m`。

### 坑 16：以为 mock 模型"变笨了"

- **症状**：`--mock` 下无论说什么都只走两个剧本，或干脆回默认介绍。
- **原因**：mock 不是模型，只是按关键词匹配预设剧本（`src/llm/mock.ts`）。它没有推理能力。
- **解决**：这是设计使然，用来离线验证循环/工具/权限。想验证模型行为就填 `.env` 用真模型；想加场景就改 `SCENARIOS`（但别改测试依赖的行为）。

### 坑 17：流式工具调用的参数拼接错

- **症状**：工具参数变成半截 JSON，或两个调用的参数串在一起。
- **原因**：`delta.tool_calls` 按 `index` 分片到达，`arguments` 是字符串片段；直接对每个分片 `JSON.parse` 必错。
- **解决**：`src/llm/client.ts:280-290` 用 `pending: Map<index, slot>` 累加，流结束时按 index 排序一次性 flush。这是全文件最容易写错的地方，测试里专门喂了分片数据。

### 坑 18：重试导致重复输出

- **症状**：网络抖一下后，用户看到同一段话出现两遍，甚至工具被执行两次。
- **原因**：流式已经吐出部分内容，重试时从头再来。
- **解决**：`src/llm/client.ts:341-367` 的 `emittedAnything` 标记——只有"一个字都没吐出来"才重试；已输出后失败就直接抛给用户。工具执行也一样：不要在已产生副作用后盲目重试。

### 坑 19：跑满 `maxSteps`，任务却没完成

- **症状**：最后提示"已达到最大步数 25，任务可能还没完成"。
- **原因**：任务太大没拆；模型陷入重复工具调用；单步工具失败后反复试。
- **解决**：调大 `--max-steps`；在提示词里让模型先用 `todowrite` 拆 3-8 步；出现重复调用时检查是不是参数一直在报错。`runAgent` 会返回 `hitStepLimit`；脚本接口 `node src/main.ts run ...` 在中断、跑满上限、工具被权限拒绝时会返回退出码 1（见 `src/main.ts:389`），CI 可以据此判失败。

### 坑 20：`bash` 超时 / 子进程杀不干净

- **症状**：命令卡死两分钟才返回；或主进程退出了，后台子进程还在跑。
- **原因**：只 kill 了 bash 本身，没杀它 fork 出来的子进程。
- **解决**：`src/tools/bash.ts` 用 `detached: true` 让子进程成为进程组组长，超时/中断时 `process.kill(-pid)` 杀整个组；默认超时 120s，上限 600s；输出超过 30 万字符截断。

## 99.3 第 0 章 4 道自测题的参考答案

> 题目在 [第 0 章 0.9 节](./00-从零理解Agent.md#09-自测题答案见第-99-章)。先自己答，再对答案。

### 第 1 题：模型说"我已读取 src/main.ts，第 10 行有 bug"，这句话可能有哪些问题？

1. **模型没有手。** 它不能读文件；"已读取"最多意味着它上一轮请求过 `read`，而不是真的读过。没看到 `tool` 消息，就不能信这句话。
2. **可能是幻觉。** 即使它真的调用过工具，也可能记错行号或编造内容——行号、报错、文件内容都要以工具返回的原始输出为准。
3. **程序怎么防**：① 只把工具返回的内容视为事实；② 每个 `tool_call` 必须对应真实执行和 `tool` 消息（`src/agent/loop.ts`）；③ 提示词明确"不要编造，工具没返回的不要假装看到"（`src/agent/prompt.ts`）；④ 关键结论让它用 `read` 再验证一遍，或跑测试证明。这正是"harness 要替模型兜底"的意义。

### 第 2 题：为什么"一次输出完整计划、程序照着执行"行不通？举反例。

因为**模型在行动前看不到行动结果**，而下一步往往依赖上一步的观察。具体反例：任务"修复测试失败"——
模型必须先跑 `npm test` 看到失败信息，才知道读哪个文件；读到源码才知道改哪一行；改完还要再跑一次
验证。计划里没法预知这些。再如"把版本号改成 0.2.0"：模型必须先 `read` 看到当前版本号和精确文本，
才能构造唯一的 `oldString`；靠猜的 `edit` 会匹配失败。所以必须 ReAct：做一步 → 看结果 → 决定下一步。

### 第 3 题：`system`/`user`/`assistant`/`tool` 分别是谁产生的？

| 角色 | 谁产生 | 例子 | 代码 |
| --- | --- | --- | --- |
| `system` | 你的程序 | "你是 mini-opencode……工作目录是……" | `src/agent/prompt.ts` 的 `buildSystemPrompt` |
| `user` | 真实用户 | "帮我创建一个 hello.txt" | `src/main.ts` 的 `runTurn`（`session.appendMessage`） |
| `assistant` | 模型（流式文本 + 工具调用请求），程序落盘 | "我先看看目录" + `tool_calls` | `src/agent/loop.ts:310-318` |
| `tool` | 你的程序执行工具后构造 | `bash` 的输出 + exit code | `src/agent/loop.ts` 的 `executeToolCall` |

### 第 4 题：给只会聊天的机器人加"查天气"，最小改动是什么？

用本章术语回答：给它加一个**工具**（`get_weather`，JSON Schema 参数 `{ city: string }`），
实现 `execute` 去调天气 API；把"单次聊天调用"换成 **agent loop**（`runAgent`）：把工具定义随请求
发给模型（**tool calling**），模型返回 `tool_call` 后由程序执行，再把结果作为 **tool 消息**回填，
带着新历史再次调用模型，直到它不再请求工具、输出最终回答。最小改动清单：
① 写一个 `Tool` 并 `registry.register`；② 用 `runAgent` 替代一次 `stream`；③ 权限上把它归类为
`exec` 或自定义类别（外部网络调用默认要确认）。这就是第 2、3 章讲的那条链路。

## 99.5 本章小结

- 术语表按"模型协议 → Agent 机制 → 工具安全 → 工程生态"分组，每个词都能在 `src/` 里找到
  落地位置；查不到实现位置的词（LSP/远程 MCP/prompt cache），就是本项目留给你的练习。
- 20 个坑可以归成四类：**协议类**（tool_call_id/JSON/流式）、**上下文类**（爆/压缩/重复）、
  **安全类**（路径/权限/危险命令/注入）、**交互类**（TTY/颜色/mock/超时）。
- 所有坑的共同解法只有一句：**把失败变成模型能看懂的反馈，而不是让程序崩掉。**
- 第 0 章 4 道题的答案如果和你想的不一样，回去重读第 0 章的 0.1~0.4 节，比继续往下读更值。
