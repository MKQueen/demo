# 第 2 章 消息、角色与工具调用协议

> **本章目标**：把"工具调用"这件事从玄学变成可验证的协议。
> 读完你能：手写一份工具定义、正确处理 `tool_calls` 和 `tool_call_id`、
> 知道模型写错参数时怎么让它自己改、并理解为什么参数校验是 Agent 的必需品。
>
> 预计：45 分钟。对应代码：`src/llm/types.ts`、`src/tools/registry.ts`、`examples/02-one-tool.ts`。

---

## 2.1 四种角色，各司其职

第 1 章简单提过，这里把它钉死。**所有 Agent 框架的消息模型，都是这四种角色的组合**：

| role | 谁产生 | 能带什么 | 例子 |
| --- | --- | --- | --- |
| `system` | 你的程序 | `content` | "你是 mini-opencode，一个编码 Agent……" |
| `user` | 用户 | `content` | "把 README 里的错别字改一下" |
| `assistant` | 模型 | `content`（可为 null）+ `tool_calls`（可选） | "我先读一下 README。" + 请求 `read` |
| `tool` | 你的程序 | `tool_call_id` + `content` | "1\| # mini-opencode…" |

三个容易搞混的点：

1. **`tool` 消息不是用户说的话**，它是程序把"工具执行结果"喂回给模型的观察结果。
2. **`assistant` 的 `content` 可以是 `null`**：当模型只想调工具、不想说话时（比如连续调三个工具），
   content 就是 null。如果你强行塞 `""` 或"我要调用工具"，有些模型会混乱。
3. **`system` 一般只有一条**，放在最前面。它是"导演"，不参与对话内容。

## 2.2 一次工具调用的完整生命周期

这是本章最该背下来的东西。假设用户说"现在几点了？"，我们的历史会这样变化：

```
初始：
  [system] 你是助手，需要时间就调用 get_time
  [user]   现在几点了？

── 第 1 次请求（带上 tools 定义）──
模型返回：
  [assistant] content=null
              tool_calls=[{ id:"call_1", function:{ name:"get_time", arguments:"{}" } }]

程序执行 get_time()，得到 "2026年11月2日 10:46:42"，然后追加：
  [tool] tool_call_id="call_1", name="get_time", content="2026年11月2日 10:46:42"

── 第 2 次请求（历史里多了上面两条）──
模型看到工具结果，返回：
  [assistant] content="我查了一下，现在是 2026年11月2日 10:46:42。"
              （没有 tool_calls，循环结束）
```

**五条消息，两轮请求，一次工具调用。** 所有 Agent（包括 opencode、Claude Code）都是这个模式，
区别只是工具多、轮数多、工程细节多。

> 🔑 记住这个对应关系：
> `assistant.tool_calls[i].id` **必须等于** 对应 `tool.tool_call_id`。
> 这是模型区分"你这个结果是在回我哪次调用"的唯一依据。对不上，接口直接 400。

## 2.3 工具定义：给模型的一份"合同"

工具不是"注册一个函数"就完事。你得给模型一份说明书，告诉它：

- 我叫什么（`name`）
- 我是干什么的（`description`）
- 我要什么参数（`parameters`，JSON Schema）

```ts
// src/llm/types.ts
export interface ToolDefinition {
  type: "function";
  function: {
    name: string;
    description: string;
    parameters: JSONSchema;
  };
}
```

一个真实的例子（`src/tools/files.ts` 的 read 工具）：

```ts
{
  name: "read",
  description: "读取一个文本文件，返回带行号的内容。大文件请用 offset/limit 分段读取。" +
               "改文件前一定要先 read，否则你可能基于过时内容做修改。",
  parameters: {
    type: "object",
    properties: {
      path:   { type: "string",  description: "文件路径（相对工作目录或绝对路径）" },
      offset: { type: "integer", description: "从第几行开始读（1 开始），默认 1", minimum: 1 },
      limit:  { type: "integer", description: "最多读多少行，默认 2000", minimum: 1, maximum: 2000 },
    },
    required: ["path"],
    additionalProperties: false,
  },
}
```

### 描述（description）为什么这么重要

**模型是唯一读这个描述的"人"。** 它决定了模型什么时候用、怎么用这个工具。

写得差的描述：

```
read：读文件
```

写得好的描述：

```
读取一个文本文件，返回带行号的内容。大文件请用 offset/limit 分段读取。
改文件前一定要先 read，否则你可能基于过时内容做修改。
```

好描述包含三件事：**做什么、什么时候用、有什么约束**。
你在写工具描述，本质上是在给模型写"使用手册"——这是提示词工程最实在的一部分。

### `additionalProperties: false` 是防呆

它告诉模型"不许自创参数"。我们的校验器（下一节）会强制执行：
模型要是传了 `file_path` 而 schema 里只有 `path`，会收到一条明确的错误：
"出现未知参数 file_path（该工具只接受：path, offset, limit）"。

这比默默忽略强一万倍——**模型看到具体错误，下一轮就能改对。**

## 2.4 `tool_calls` 的四个细节

### 细节 1：`arguments` 是 JSON **字符串**

看这个类型定义（`src/llm/types.ts`）：

```ts
export interface ToolCall {
  id: string;
  type: "function";
  function: {
    name: string;
    arguments: string;   // ← 注意：string，不是 object
  };
}
```

为什么是字符串？因为模型是"逐字生成"的，它只能吐文本。所以你会收到：

```json
"arguments": "{\"path\":\"src/main.ts\",\"limit\":100}"
```

你的代码里必须 `JSON.parse`。而且**必须处理解析失败**——模型写坏 JSON 是常事（少引号、多个逗号）。

### 细节 2：id 与 tool_call_id 必须配对

- `assistant.tool_calls[i].id` 是模型生成的（如 `call_abc123`）
- `tool.tool_call_id` 必须是同一个字符串
- 一个 assistant 消息里可以有**多个** tool_calls（并行调用），每个都要有对应的 tool 消息

### 细节 3：并行调用

模型完全可能一轮里要求调三个工具：

```json
"tool_calls": [
  { "id": "call_1", "function": { "name": "read", "arguments": "{\"path\":\"a.ts\"}" } },
  { "id": "call_2", "function": { "name": "read", "arguments": "{\"path\":\"b.ts\"}" } }
]
```

程序要把每个都执行，然后**按顺序**塞三条 tool 消息回去。真实实现里可以并发执行以提速，
但回填的顺序通常要保持和 tool_calls 一致（有些模型对顺序敏感）。

### 细节 4：流式分片

如果 `stream: true`，工具调用不是一次性给你的，而是这样来的：

```json
data: {"choices":[{"delta":{"tool_calls":[{"index":0,"id":"call_1","type":"function","function":{"name":"read","arguments":""}}]}}]}
data: {"choices":[{"delta":{"tool_calls":[{"index":0,"function":{"arguments":"{\"pa"}}]}}]}
data: {"choices":[{"delta":{"tool_calls":[{"index":0,"function":{"arguments":"th\":\"a.ts\"}"}}]}}]}
```

注意：**只有第一个分片带 `id` 和 `name`，后面的只带 `arguments` 片段，靠 `index` 归组。**
所以客户端必须自己拼（`src/llm/client.ts` 的 `streamOnce` 里用 `Map<number, ToolCallSlot>` 做这件事）：

```ts
const slot = pending.get(index) ?? { id: "", name: "", args: "" };
if (part.id) slot.id = part.id;
if (part.function?.name) slot.name = part.function.name;
if (part.function?.arguments) slot.args += part.function.arguments; // 字符串拼接
pending.set(index, slot);
```

这就是为什么 `ToolCall.arguments` 是字符串——它在网络上本来就是一段一段拼出来的。

## 2.5 最重要的一句话：模型不执行任何东西

再强调一次，因为这是 Agent 安全模型的根基：

> 模型输出的 `tool_calls` 只是一段 **"请求"**。
> 它没有读文件、没有跑命令、没有联网。执行这些的是**你的程序**。

推论：

1. **你给什么工具，它就能干什么**；不给 `bash`，它永远跑不了命令。
2. **权限系统是有意义的**：在执行前拦截，模型完全无法绕过（它只能"再请求一次"）。
3. **工具描述可以被骗**：如果模型读到恶意 README（提示注入），它可能"请求"危险操作——
   但请求到执行之间，还有你的一道权限闸门（第 5 章）。

## 2.6 参数校验：让 Agent 学会自己纠错

模型会写错参数。这不是偶尔，是常态：

- JSON 语法错（少引号、尾逗号）
- 参数名拼错（`path` 写成 `file_path`）
- 类型错（`limit: "10"` 字符串）
- 缺必填参数
- 编造一个不存在的工具名

如果你直接 `JSON.parse` 然后调用函数，程序就崩了（或者更糟：带着错误参数执行了危险操作）。

正确做法：**解析 → 校验 → 把错误喂回去，让模型自己改**。

`src/tools/registry.ts` 里的 `validateArgs` 干的就是这件事（手写 JSON Schema 子集校验器，约 100 行）：

```ts
const validation = validateArgs(tool.parameters, parsed);
if (!validation.ok) {
  return { isError: true, output: formatValidationErrors(validation.errors) };
}
```

模型收到的是这样一条 tool 消息：

```
参数校验失败：
- 缺少必填参数 "path"
- limit 应该是整数，收到的是 string
请修正参数后重新调用这个工具。
```

下一轮它就会改对。**这就是 Agent "自我纠错"的真实机制**——不是模型变聪明了，
而是你把错误信息结构化地喂回给了它。

在 `src/agent/loop.ts` 的 `runToolSafely` 里，这套流程有五步：

```
1. 未知工具 → 告诉它有哪些工具
2. JSON 解析失败 → 告诉它原始参数和解析错误
3. schema 校验失败 → 逐条列出哪个字段错了
4. 权限检查 → 拒绝时说明原因
5. 真正执行 → 执行抛异常也转成错误消息返回
```

**任何一步失败，都不会让程序崩溃，只会让模型看到一条错误消息。** 这个设计是 Agent 鲁棒性的关键。

## 2.7 动手实验

**实验 1：跑一遍协议（离线可跑）**

```bash
node examples/02-one-tool.ts --mock
```

观察输出里的四个关键点：
1. 请求里的 `tools` 定义长什么样
2. 模型返回的 `tool_calls`（只是 JSON！）
3. 程序执行后得到的真实时间
4. 第二次请求里多出来的 `tool` 消息

**实验 2：故意破坏协议（需要真模型）**

改 `examples/02-one-tool.ts`，把回填的 `tool_call_id` 删掉：

```ts
messages.push({
  role: "tool",
  // tool_call_id: call.id,   ← 注释掉
  name: call.function.name,
  content: output,
});
```

再跑一次。你会发现接口直接报 400（类似 `tool_call_id is required`）。
**记住这个报错**——第 99 章的「20 个常见坑」里它排第 4。

**实验 3：让模型自己纠错（需要真模型）**

把 `get_time` 的 description 改成误导性的："获取股票价格"。再问"现在几点"，
看模型会不会调错工具、你该怎么改描述让它调对。
（这就是"工具描述即提示词"的体感。）

**实验 4：看参数校验怎么救场（离线可跑）**

在 `test/loop.test.ts` 里找到"参数 schema 不合法"那个测试，跑：

```bash
npm test
```

它构造了一个 `echo(text: 123)` 的非法调用，断言模型收到"text 应该是字符串"。
这就是校验器的行为被钉死在测试里。

## 2.8 常见坑

| 坑 | 症状 | 原因 / 解决 |
| --- | --- | --- |
| 直接调 `JSON.parse(arguments)` 不兜底 | 偶发崩溃 | 模型会写坏 JSON；必须 try/catch 并回喂错误 |
| `tool_call_id` 对不上 | 接口 400 | 用 `assistant.tool_calls[i].id` 原样回填，别自己造 |
| 忘了给每个 tool_call 回一条 tool 消息 | 接口 400 / 模型行为异常 | 并行调用时逐个回填，一个都不能少 |
| assistant content 写成 `""` | 部分模型报错 | 只调工具时用 `null` |
| 工具描述太模糊 | 模型不用 / 用错工具 | 描述里写清"什么时候用、参数怎么给、有什么限制" |
| schema 太复杂（深层嵌套 anyOf） | 模型生成参数困难 | 工具参数尽量扁平、简单；复杂参数用字符串传 JSON |
| 把模型返回的工具调用当真执行了 | 安全灾难 | 永远先校验 + 权限检查，再执行 |

## 2.9 本章小结

- 四种角色：system（规则）、user（输入）、assistant（模型）、tool（观察结果）。
- 一次工具调用 = assistant 带 `tool_calls` + 程序执行 + tool 带 `tool_call_id` 回填 + 再请求。
- `arguments` 永远是 JSON 字符串，且流式时是分片到达、按 `index` 拼接。
- 模型只"请求"调用，不执行；执行的是你的代码——这是权限系统存在的前提。
- 工具描述的读者是模型，"做什么 + 何时用 + 什么约束"三件套。
- 参数校验 + 错误回喂 = Agent 自我纠错；五步防护让工具永远不把程序搞崩。
