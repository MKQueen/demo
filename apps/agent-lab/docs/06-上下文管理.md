# 第 6 章：上下文管理

> **本章目标**：理解为什么 Agent"聊着聊着就崩了"，以及三层防御怎么把历史压进预算：截断工具输出 → 按轮裁剪 → LLM 摘要压缩。
> 读完你应该能解释：为什么不能按条删消息、为什么压缩切点要回退、为什么摘要消息用 `assistant` 角色、为什么压缩之后 prompt cache 反而可能失效。
>
> 预计：35 分钟。

---

## 6.1 先建立直觉：模型没有记忆，是你在替它背行李

第 0 章说过：模型没有记忆，每次调用都要把**全部历史**重新发一遍。它像个每句话都失忆的顾问——你必须每次把之前发生的事完整复述给它。

而"之前发生的事"里，工具输出是大头：读一个 200 行文件几千字符，跑一次测试几百行日志，再 `grep` 一遍……用 `estimateTokens` 粗算，1 个汉字约 1.1 token，几轮下来轻松上万 token。

模型的**上下文窗口（context window）**是有限的，而且不同模型差别很大：DeepSeek V4 系列标称 **1M token**，GPT-4o 约 128K——窗口越满越贵、越慢、越容易走神。于是你会看到：Agent 前几轮很聪明，工具一多就开始重复劳动、忘掉目标，甚至 API 直接报"context length exceeded"。所以上下文管理不是"性能优化"，是**正确性问题**：不管理，Agent 一定会在某个时刻崩掉。源码在 `src/agent/context.ts`，调用点在 `src/agent/loop.ts`，手动入口是 `src/main.ts` 的 `/compact`。

## 6.2 核心概念逐条拆

### 概念 1：窗口、预算与 `contextBudget`

窗口是模型一次能接收的 token 上限；预算是你自己划的"历史最多占多少 token"的红线。项目不再写死预算，而是按模型名查窗口表、由 `contextBudgetForModel()` 算出安全预算（`config.ts` 的 `MODEL_CONTEXT_WINDOWS`）。注意表里对 DeepSeek 是**刻意保守**的：官方 V4 标称 1M，但我们默认按 256K 估，算出 **224K** 预算；GPT-4o 128K → 112K，认不出的模型按 128K → 112K。为什么不直接按 1M 算？因为提示词、工具定义、模型输出都要占地方，而且一次塞太满既慢又贵、还容易“中间失忆”。真需要更长可以 `--budget 400000` 手动放大。这样换模型时"记忆"会自动变长，不会被一个 24K 的小默认值白白裁掉历史。仍可覆盖：命令行 `--budget`、`.env` 的 `MINI_CONTEXT_BUDGET`，或网页「模型配置」里的 contextBudget 输入框（1000~2000000）。

### 概念 2：token 估算——便宜、够用、宁可高估

精确计数要用对应模型的 BPE 分词器（如 tiktoken），还要几 MB 词表；教学项目用启发式：`Math.ceil(cjk * 1.1 + other / 3.5)`。中文/日文/韩文/全角符号按 1.1 token/字，其它字符约 3.5 个算 1 token。实测：21 个汉字 → 18 token，54 个英文字符 → 16 token。`messageTokens` 还会给每条消息加 4（role 等格式开销）、每个 tool_call 加 8。误差存在，但方向可控：`other / 3.5` 比真实 `~4 字符/token` 更保守，中文按 1.1 也偏高。上下文管理的目标是"别超"，所以宁可高估。

### 概念 3：三层防御总览

`context.ts` 把防御分成三层，一层比一层贵：

1. **截断单条工具输出**：单条 tool 消息最多留 `MAX_TOOL_OUTPUT_CHARS = 2000` 字符，用 `truncateMiddle` 保头尾，末尾加提示"原始输出共 N 字符，已截断，需要细节请重新精确查询"。
2. **按整轮裁剪历史**：预算还超，就从最老的"轮"开始删。一条 `user` 开启一轮，直到下一条 `user` 之前的所有消息算一整轮。
3. **LLM 摘要压缩**（`compactHistory`）：把旧历史交给模型总结，用摘要替换原文。最贵但最不丢信息，真实 opencode 的 auto-compact 就是它。

大多数情况第一层就够；预算很紧时第二层兜底；想"记得住但省 token"时用第三层。

### 概念 4：为什么必须"整轮删"而不是按条删

OpenAI 协议要求：assistant 消息里的每个 `tool_calls[i]`，后面都必须有一条 `tool_call_id` 相同的 tool 消息回应。按条删会拆散它们，下一轮请求直接被 API 拒绝（400）。

所以 `fitContext` 先找第一条和最后一条 user：只剩最后一轮时停手（删了模型就不知道你在问什么）；否则把"第一条 user 到第二条 user 之前"整段切掉。测试里专门断言了裁剪后 `tool` 的 id 序列和 `assistant` 的 `tool_calls` id 序列完全一致。

另一个细节：`fitContext` **不修改传入的数组**（先 `map` 复制、再对新数组 `splice`），因为外面还持有原历史——要写会话文件、要展示。同样的协议约束对摘要压缩也成立：`compactHistory` 的切点也必须保证不拆散 tool 配对（见概念 5）。

### 概念 5：`compactHistory` 的切点、prompt 与角色

它先把历史切成 `older` / `recent` 两段，切点的确定比"取最后 keepRecent 条"复杂：先算 `cut = max(0, length - keepRecent)`；如果切点落在 tool 消息上，就向前退到不是 tool；再向前退到最近一条 user（尽量让 `recent` 从一轮开头开始）；退无可退（`cut <= 0`，只剩一轮）就抛"历史太短"。然后 `older` 拼成纯文本（每条内容截 800 字、工具参数截 200 字、整体截 24000 字），交给模型，用一段 system prompt 要求保留：**用户目标、已完成的动作、当前状态、未解决的问题**，不要编造。

几个坑被提前防住：transcript 本身会超长（所以层层截断）；摘要请求用 `temperature: 0.1`（要稳定不要发挥）；摘要为空就抛错；合并后还要做一次 **tool 配对校验**（每条 tool 的 `tool_call_id` 必须能在前面的 `assistant.tool_calls` 里找到）；如果 `after >= before` 就抛错放弃（摘要本身也是 token，短历史压缩是负收益）。

合并时摘要消息用 **assistant** 角色而不是 system：不改变系统提示词的权威性，也让消息序列更像真实对话；`recent` 原样保留（通常略多于 keepRecent 条，因为回退到了轮边界）。顺带记一个真实 bug：旧实现直接 `slice(-keepRecent)`，验收时用 6 轮 fixture（18 条）复现——切点正好落在 `assistant(tool_calls)` 和 `tool` 之间，`/compact` 后接真模型必 400；修复就是上面的切点回退，测试在 `test/unit.test.ts` 的 `compactHistory: 绝不把 assistant.tool_calls 和 tool 结果拆散`。

### 概念 6：自动压缩的触发条件与失败回退

`loop.ts` 在**每轮调模型之前**检查 `rawTokens > contextBudget && history.length >= 8`。两个条件都要满足：`history.length >= 8` 避免历史很短时就浪费一次模型调用做压缩（压缩要钱要时间，且历史太短时摘要会丢掉仅有的上下文）。

成功时用 `splice(0, history.length, ...)` **原地替换**历史（`history` 的所有权在主循环，直接赋值只改局部变量），给会话追加 `compaction` 事件（before/after/summary，可审计），并 `notice` 告诉用户；失败**不是致命错误**（比如"历史太短""压缩没有减少 token"）：`notice` 一句后继续，`fitContext` 的裁剪会兜底。如果失败原因是用户中断，则按中断处理直接返回。

### 概念 7：手动 `/compact` 与 prompt cache

REPL 里 `/compact` 调 `main.ts` 的 `handleCompact`：同一个 `compactHistory`、`keepRecent: 4`，成功后原地替换历史、追加带 `manual: true` 的 `compaction` 事件、打印压缩前后 token 和摘要前 400 字；失败只报错，不影响使用。

还有一个真实产品很在意、本 mini 版没实现的点：**prompt cache（提示缓存）**。很多模型服务会缓存"相同前缀 token"，同一段前缀第二次出现更便宜、首 token 更快。Agent 每轮发的都是 `system + 最近历史`，天然有大量重复前缀，缓存收益巨大。**但裁剪和压缩会改动历史前缀**，缓存命中率会掉，甚至总成本反而上升。真实实现会在"压不压、压多少"之间算总账；我们这里只留概念。

## 6.3 代码导览

### 6.3.1 `fitContext`：先截断，再整轮裁剪

```ts
let working: ChatMessage[] = messages.map((message) => {
  if (message.role !== "tool" || typeof message.content !== "string") return message;
  if (message.content.length <= MAX_TOOL_OUTPUT_CHARS) return message;
  truncatedToolOutputs++;
  return { ...message, content: truncateMiddle(message.content, MAX_TOOL_OUTPUT_CHARS) +
    `\n[提示] 原始工具输出共 ${message.content.length} 字符，已截断。需要细节请重新精确查询。` };
});

// —— 第二层：从最老的"轮"开始删 ——
while (tokens > budget && working.length > 2) {
  const firstUser = working.findIndex((m) => m.role === "user");
  if (firstUser === -1) break;
  const lastUser = working.findLastIndex((m) => m.role === "user");
  if (firstUser === lastUser) break; // 只剩最后一轮，不能再删
  const nextUser = working.findIndex((m, i) => i > firstUser && m.role === "user");
  const dropCount = (nextUser === -1 ? working.length : nextUser) - firstUser;
  working.splice(firstUser, dropCount);
  removed += dropCount;
  tokens = estimateMessagesTokens(working);
}
```

第一层只处理 role 为 tool 的字符串内容（`...message` 浅拷贝、提示"需要细节请重新精确查询"）；第二层每次删一整轮，删完重算 token。`working.length > 2` 和 `firstUser === lastUser` 是两道保险，保证至少留下最后一轮。循环后面还有**兜底**：若单条消息本身超长（比如用户粘了 10 万字），把所有超过 1200 字符的内容再硬截一次——这段不计入 `removed` / `truncatedToolOutputs`，后面"常见坑"会讲。

### 6.3.2 `compactHistory`：先找安全切点，再请求与合并

```ts
let cut = Math.max(0, options.messages.length - keepRecent);
while (cut > 0 && options.messages[cut]!.role === "tool") cut--;      // 1) 别从 tool 开始
let userAtOrBefore = -1;                                               // 2) 回退到轮开头
for (let i = cut; i >= 0; i--) {   // （原文件展开成三行，这里压缩排版）
  if (options.messages[i]!.role === "user") { userAtOrBefore = i; break; }
}
if (userAtOrBefore > 0) cut = userAtOrBefore;
if (cut <= 0) throw new Error("历史太短，不需要压缩");                  // 3) 只有一轮，放弃
const older = options.messages.slice(0, cut);
const recent = options.messages.slice(cut);
const transcript = older
  .map((message) => {
    const content = typeof message.content === "string" ? message.content : "";
    const calls = message.tool_calls
      ?.map((call) => `[请求调用 ${call.function.name}(${truncateMiddle(call.function.arguments, 200)})]`)
      .join(" ") ?? "";
    return `${message.role.toUpperCase()}: ${truncateMiddle(content, 800)} ${calls}`.trim();
  })
  .join("\n")
  .slice(0, 24_000);

const request: ChatMessage[] = [
  { role: "system", content: "你是一个上下文压缩器。把下面的对话历史压缩成一段简洁的中文摘要。必须保留：用户的目标、已完成的动作（改了哪些文件、跑了什么命令）、当前状态、尚未解决的问题。不要编造没有发生的事，不要输出多余的解释。" },
  { role: "user", content: transcript },
];
const merged: ChatMessage[] = [
  { role: "assistant", content: `[早前对话摘要]\n${summary}` },
  ...recent,
];
```

切点回退是为了守住协议：只要 `recent` 从 user 开始，后面每个 `assistant.tool_calls` 都会带着它的 tool 结果一起进来。system 里的"上下文压缩器"是**协议**：mock 模型靠它识别"这是压缩请求"，返回假摘要、不按剧本演戏；transcript 给每条消息加角色前缀和工具调用名，模型才知道"谁做了什么"。摘要用 assistant 角色、加 `[早前对话摘要]` 前缀，模型才知道这不是用户说的话。

### 6.3.3 自动压缩的调用点

```ts
const rawTokens = estimateMessagesTokens(history);
if (rawTokens > contextBudget && history.length >= 8) {
  try {
    const compacted = await compactHistory({ messages: history, provider, signal, keepRecent: 4 });
    history.splice(0, history.length, ...compacted.messages);
    options.session?.appendEvent({ type: "compaction", before: compacted.before,
      after: compacted.after, summary: compacted.summary, at: nowIso() });
    ui.notice(`上下文已自动压缩：约 ${compacted.before} → ${compacted.after} tokens（旧历史变成一段摘要）`);
  } catch (err) {
    if (signal.aborted || isAbortError(err)) return { steps: steps - 1, usage, aborted: true, hitStepLimit: false };
    ui.notice(`自动压缩失败（${messageOf(err)}），将使用裁剪后的上下文继续。`);
  }
}
const fitted = fitContext(history, contextBudget);
```

（`appendEvent` 字段和 notice 文案有省略）压缩尝试在**裁剪之前**：先试最不丢信息的方案，不行再降级。

## 6.5 常见坑

**坑 1：按条删历史，结果 API 报 400**
- 症状：裁剪后下一轮请求报 `tool_calls` / `tool_call_id` 不匹配。
- 原因：协议要求每个 `tool_calls[i]` 都有对应的 tool 消息；按条删、或压缩切点没对齐轮边界，都会拆散它们（旧版 `compactHistory` 的 `slice(-keepRecent)` 就在 6 轮 fixture 上翻过车）。
- 避免：像 `fitContext` 一样**按整轮删**，压缩切点回退到轮边界，删完检查 id 配对（`test/unit.test.ts` 有专门用例）。

**坑 2：预算设得太小，兜底截断也救不回来**
- 症状：`fitContext` 返回的 `tokens` 仍大于 `budget`，而且 notice 里没提。
- 原因：兜底硬截断最多把单条砍到 1200 字符（中文约 1320 token），预算更小就无解；而且兜底**不计入** `removed` / `truncatedToolOutputs`，notice 不一定会打印。
- 避免：预算别设离谱（默认按模型窗口自动算，DeepSeek 约 224K）；看真实占用要看 `fitted.tokens`，别只看 notice。

**坑 3：压缩后 Agent "失忆"、重复劳动**
- 症状：自动压缩之后它重新执行做过的步骤，或忘了最初目标。
- 原因：摘要必然丢细节；`keepRecent=4` 之外的精确内容（文件路径、报错原文）没了。实验 3 里 mock 恢复会话后就把第一轮场景重演了一遍，是这现象的夸张版。
- 避免：把关键状态写进文件或 todo（`src/tools/todo.ts` 的 todowrite 工具就是"外部记忆"）；压缩后让重要文件重新 `read` 一次。

**坑 4：把估算当精确值，卡着窗口用**
- 症状：预算设成和模型窗口一样大，真实请求还是超长。
- 原因与避免：`estimateTokens` 是启发式，误差可能 10%+，还要给输出留空间——预算取窗口的 1/3～1/2 量级，并留足余量。

**坑 5：忽略 prompt cache 的成本**
- 症状：上下文管理"省了 token"，账单反而变贵、首字延迟变高。
- 原因与避免：裁剪/压缩改动了历史前缀，破坏服务端提示缓存命中；真实产品要按"省下的 token vs 丢掉的缓存"算总账，而不是无脑压。

---

## 6.6 本章小结

- 模型没有记忆，每轮都要重放全部历史；工具输出是大头，不管上下文，Agent 一定会崩。
- `contextBudget` 是你自己划的红线（默认按模型窗口的 7/8 自动算），要给系统提示词和模型输出留余量。
- `estimateTokens` 用 `cjk * 1.1 + other / 3.5` 廉价估算，宁可高估；精确计数要靠分词器，教学版不值得。
- 三层防御：单条工具输出截断（2000 字符）→ 按整轮裁剪 → LLM 摘要压缩。
- 裁剪必须整轮删、保留最后一条 user、不改原数组；否则要么 API 报错，要么丢当前问题。
- `compactHistory` 先把切点回退到轮边界（防拆散 tool_calls/tool 配对），再转文本 + 固定 prompt + assistant 摘要；压不动或配对非法会抛错，回退到裁剪。
- 自动压缩条件 `rawTokens > contextBudget && history.length >= 8`，每轮模型调用前检查，压缩事件写入会话；手动 `/compact` 走同一个函数。prompt cache 意味着"压缩不一定省钱"，要算总账。

## 6.7 练习

1. **给 `fitContext` 加"保留含关键字的旧消息"**：比如保留所有含"报错/error"的旧轮，其余整轮删。提示：删完还要保证 assistant/tool 配对，别拆散一轮；想想怎么定位"哪几轮含关键字"。
2. **改进摘要 prompt**：要求摘要额外输出"下一步计划"和"关键文件清单"两节。提示：改 system prompt 后 mock 的假摘要不会变——怎么验证它真的影响了真实模型？
3. **给自动压缩加节流**：现在小预算下每轮都会压。提示：加"距上次压缩至少隔 N 轮"或"压缩后 token 必须降 X% 才保留"，想清楚状态存在哪（`AgentRunOptions` 还是会话事件）。
