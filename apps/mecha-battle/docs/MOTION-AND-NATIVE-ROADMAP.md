## 产品方向

体感是主要输入，键盘/手柄承担备用和菜单操作。以《Override 2》的巨型机甲第三人称格斗、清楚的攻击预兆、近远程距离管理、城市尺度和短局对战节奏作为设计参照。重点做好一台机甲、一只怪兽、一个可玩街区，然后扩展。

人体追踪输出“攻击意图 + 连续身体状态”。待机时手臂可以适度跟随玩家；确认出拳后由完整动画、承诺窗口、IK、空间碰撞和受击反馈执行攻击。不能把摄像头每帧的手腕位置直接作为武器碰撞点，否则抖动会变成乱挥、不同身高臂长会改变攻击范围。

先以半身可玩为基线，让头肩肘腕进入画面即可。全身入镜时才启用踏步；不把玩家真的跑动、跳跃或踢腿作为基础通关条件。喷气位移、短飞等动作应单独设计低疲劳手势并做冲突测试，而非继续往已有拳击判定里叠阈值。

## 本轮已落地：显式追踪流水线

摄像头帧 → EfficientDet Lite0 的 person 检测 → 中央玩家确认与矩形关联 → 扩展玩家区域 → Pose Landmarker 33 点 → 映射回整幅画面 → 可见度校验/时间平滑 → 站定校准 → 连续输入与离散动作。

MediaPipe Pose VIDEO 本身已有内部检测/跟踪。本轮补的是游戏可管理的外部玩家锁定、多人选择规则、可视化和输入门控，不将它描述为从零实现人体识别。

- 人物检测独立于骨骼；当前 worker CPU 路径约每 250ms 检测人物，整条链路上限 22Hz 调度，一次仅一帧在途。实际频率取决于相机、推理耗时与渲染，不保证达到上限。
- 人物在中央连续确认至少 350ms / 3 次检测后才锁定。已有锁定按重叠、位置和尺寸关联；短暂丢失先保留原位置，最多约 2 秒，再重新寻找中央玩家。
- 对锁定区域扩边，给伸展手臂留空间；归一化骨骼映射回原始相机坐标，保持 z 的尺度。镜像只在显示/动作分析边界各自处理一次。
- 人物丢失、骨骼不合格、摄像头断开或帧停滞会清空连续输入、积攒的动作和上一帧速度历史。恢复后重新校准，避免补发误拳。旧离散事件超过 200ms 丢弃，骨骼停滞超过 500ms 失效。
- 体感战斗连续约 0.9 秒没有有效输入会暂停；恢复锁定、校准后由玩家点击继续。
- 预览可看到检测框、锁定框、骨骼、追踪状态、人物数与单次推理耗时；视频与骨骼使用相同 contain 显示，修正 cover/拉伸错位。支持重新锁定与校准。

代码边界：`playerTracker.js` 负责检测框处理/关联；`motionSession.js` 负责校准、有效性与输入输出；`poseCamera.js` 负责浏览器摄像头、模型运行和叠画；`gesture.js` 负责动作分析。前两者和动作分析均不依赖 Three.js/DOM。

### 当前限制与验收

这版是矩形几何关联，不含人脸身份、外观特征重识别或逐帧光流。两个人重叠、快速交叉、尺寸相近时仍可能误关联；公开测试图也可能被识别为人，不具有活体检测。多人抢控、遮挡和不同真实房间仍需实拍回放验收。

当前模型推理已迁入独立 Web Worker，人物关联、手势、校准与叠画留在主线程。单次推理耗时不等于摄像头到屏幕的总延迟。桌面迁移必须将推理独立运行并测量端到端延迟。

已增加自动检查：中央确认、遮挡不切到远处路人、重捕校准、区域坐标映射、异常骨骼、无效输入归零、事件时效、停帧处理；公开 MediaPipe pose.jpg 测试图经合成摄像头跑真实两阶段模型，检查 33 点、空画面、恢复、手动重锁、摄像头停止和战斗暂停恢复。这些不是玩家真人运动识别率或性能基准。

## 原生引擎选择：Unity LTS + URP

桌面版采用 Unity LTS、URP 和 C#，先面向 Windows x64 与 macOS Apple Silicon。本机安装并激活 Personal 许可后，最小接入工程调整为 Editor 2022.3.62f3c1 / URP 14.0.12；工程已编译、导入并构建本机 Mac ARM64 训练程序，实际接收器的 TCP 输入与断开归零测试通过；完整原生游戏尚未完成。

| 路径 | 对本项目的意义 | 取舍 |
|---|---|---|
| Unity + URP | Animator、Animation Rigging、Cinemachine、粒子、物理、输入抽象与桌面发布链适合本项目 | 推荐；须验证相机与推理桥接在 Win/Mac 的实际兼容性 |
| Godot 4 | 原生桌面、开源、轻量，适合可控范围的 3D 项目 | 可行备选；较多角色工具和推理接入需自行集成 |
| Unreal | 高质量渲染、动画与物理工具较完整 | 本项目现阶段迭代和硬件成本较高；先不采用 |
| Electron / Tauri 包装 | 可把现有网页分发为桌面窗口 | 可作过渡工具，但不会自动获得游戏引擎的动画、物理和资源管线 |

Unity 支持桌面平台并不代表任意 MediaPipe 插件同时支持两平台。不要先依赖未验证的第三方 GPU 插件再设计全部游戏。

### 推理与游戏分开

第一版原生验证已采用本机独立体感进程：MediaPipe Python Tasks CPU 推理，Node 协调并复用现有动作分析，向 Unity 提供仅限本机 TCP 的有序 JSONL 输入。平台相机和最终依赖打包仍需分别验证。只传输入帧和必要的调试骨骼，不传视频到远端。开发时侧进程单独启动，发布时由游戏管理其启动、退出和错误恢复。

独立进程有故障与调试边界，也避免模型推理阻塞 Unity 渲染线程；它不是性能承诺。先测 Windows x64 和 macOS arm64 的相机帧率、CPU 占用、内存、延迟，再决定是否改为平台原生 C++/推理后端。生产打包不能要求玩家安装 Python 或打开浏览器。

浏览器提供 `PoseCamera.getInputFrame()` / `MotionSession.frame()` 的 v1 输入帧，机器可读约定在 `MOTION-INPUT-V1.schema.json`。本机通信服务已验证，Unity 接收器源文件位于 `native/unity`，仍待 Editor 编译与训练场景实机验收；schema 和传输通过不等于引擎接入完成。

输入帧含版本、递增序号、发送端单调时钟、锁定代数、有效状态、质量、连续控制、手臂状态和离散事件。`playerId` 只标识本次锁定，不是人的持久身份。`frame()` 会消费事件；同一提供者只应有一个输入消费者，调试界面读取状态不能抢走事件。

原生接收器必须：只接本机来源；拒绝未知版本、非有限数值和过大帧；按序号拒绝重复/乱序包；用接收端本地时钟检测断流，不能直接拿两进程的单调时间相减；断流 500ms 立即输出中立输入并清空技能；事件过期后丢弃；重新连接分配新的连接会话并重新校准。输入适配器输出同一份 PlayerIntent，键盘/手柄也走这个入口。

## 迁移顺序与可验收成果

1. **独立体感验证器**：真实相机选择、玩家锁定、骨骼显示、校准、录制/回放骨骼输入。先验证 Win/Mac 原生依赖与运行时，不重做整座城市。
2. **Unity 最小接入关卡**：一台机甲、一个地面、固定镜头，接同一份 PlayerIntent；体感移动/拳击/格挡成立，键盘可对照，丢人暂停有效。两个平台都构建运行后再扩内容。
3. **搬运动作与战斗规则**：现有 `.blend` / 纹理可以进入新资源管线，JS/Three.js 游戏逻辑需要移植成 C#，不能直接复制运行。先迁一记重拳、刀斩、推进攻击和一只怪兽；保留实体接触、打空、承诺、硬直和取消规则。
4. **统一角色表演与镜头**：Animator 动作状态、Animation Rigging 落脚/瞄准、Cinemachine 战斗镜头、喷气与受击。尾链/下颌和完整攻击重制继续作为角色资产任务，换引擎本身不会修好它们。
5. **做完整短局**：体感教学 → 接敌 → 阶段战 → 结束/评价 → 重试。城市倒塌参与换位和遮挡。先保证体感低疲劳、反馈清楚，再加机甲数量与模式。
6. **双平台发布验收**：Win 相机权限与驱动；Mac 摄像头用途说明、沙盒/权限、签名与公证；分辨率、全屏、存档、输入切换、推理进程回收和离线资源。分别做干净机器安装测试。

第一轮原生验收目标（尚未实测）：参考机器 1080p 游戏渲染 60fps、体感有效帧不少于 20Hz；端到端动作延迟中位数 ≤120ms、P95 ≤180ms；站定 2 分钟无误触发攻击；每种核心动作每人 20 次，至少覆盖 5 位不同身高/站距玩家，单独报告漏判/误判和遮挡恢复时间。未达标先修输入，不加角色与特效。
